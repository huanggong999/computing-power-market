## Context

现有独立 CPU 购买能力已接入算力市场和实例管理页，但购买页把输入控件的范围限制当作完整校验，提交接口仍可能同步等待云端创建完成。CPU 创建可能持续数分钟，导致用户看到长时间等待或请求超时后无法判断实例是否已受理。实例管理页的 CPU Tab 还是临时的简化表格，和 GPU Tab 的统计、筛选、详情交互不一致；同时 GPU 上游实例列表是通用实例集合，当前门户 DTO 未保留来源字段，存在 CPU 实例进入 GPU 列表并被 GPU 释放路径处理的风险。

本变更只修正现有 CPU/GPU 用户端体验和来源边界，不改变独立 CPU API、GPU Pod API 的业务语义，也不引入新的购买计费模型。

## Goals / Non-Goals

**Goals:**

- 在 CPU 购买提交前完成确定性的前端校验，并沿用已确认的参数范围。
- 提交后立即显示“已受理/创建中”，允许用户离开页面后从 CPU 列表继续查看状态。
- 统一 CPU 状态标签、失败信息、列表布局、筛选、空状态、分页和详情体验，使其与 GPU Tab 一致。
- 从 `/cloud/gpuInstance` 页面移除所有创建/购买入口，CPU 购买入口只存在于算力市场。
- 保留并传递 `origin` 等实例来源字段，在 GPU 列表和生命周期操作处建立双重隔离。

**Non-Goals:**

- 不修改系统盘、数据盘、数量和时长的既定范围：`20–2048`、`0–8192`、`1–10`、`1–36`。
- 不实现 CPU 购买价格试算、支付流程或公网 IP 计费切换。
- 不把 GPU 与 CPU 合并为一套后端生命周期接口。
- 不改变既有 GPU 创建、资源变更、监控和订单行为。

## Decisions

### 1. 购买校验采用“表单规则 + 提交前纯函数”双层校验

页面继续使用现有输入控件范围，但增加表单级错误提示，并在提交函数中再次执行纯函数校验。提交前校验地域和可用区的关联、规格是否来自当前区域接口、按量计费是否忽略时长、包月/包年时长是否为有效整数，以及所有数值是否在约定范围内。这样可以覆盖手动输入、路由恢复和测试调用等绕过控件限制的场景。

**替代方案**：只依赖后端校验。后端仍是最终权威，但不能解决用户在提交后才发现明显输入错误的问题，因此不采用。

### 2. CPU 创建采用“接受即脱离页面等待”的状态模型

购买接口返回成功且带有实例记录时，前端立即将每条实例归一化为 `creating`（若服务已返回终态则保留终态），展示“创建中”结果，并刷新 CPU 列表。页面不把云端实例变为 `running` 作为购买请求完成条件。CPU 列表刷新时以服务端状态为准；若接口响应包含 `failed`、`error` 或失败消息，则展示失败状态和原因。网络超时只提示“请求状态未知/请到列表确认”，不能直接把实例标记为失败。

**替代方案**：继续延长 Axios/RestTemplate 超时。创建时间不可控，延长超时会阻塞页面并放大网关超时风险，因此不采用。

### 3. CPU Tab 复用 GPU 页面壳，保留 CPU 专属数据映射

实例页面顶部、Tab、统计卡片、筛选区、表格容器、分页和详情抽屉使用统一布局组件或统一样式。CPU 表格只展示 CPU 有意义的字段：实例、状态、CPU/内存、系统盘/数据盘、网络/SSH、计费、操作；GPU 专属监控和 VNC 操作不出现在 CPU 行上。CPU 详情使用与 GPU 相同的侧边面板结构，但字段按 CPU 模型渲染。

`/cloud/gpuInstance` 页面隐藏顶部“创建实例”按钮，CPU Tab 内移除“购买 CPU 实例”按钮；算力市场仍负责进入购买流程。

### 4. 来源字段由后端保留，列表和操作两侧都校验

扩展 GPU 上游列表 DTO 和 VO，保留 `origin`、GPU 能力或等价来源标识。GPU 列表转换时只接受 GPU 来源或明确存在 GPU 资源的实例，并重新计算过滤后的总数；CPU 列表只接受 `origin=cpu_instance`。GPU 详情、开关机和释放前再次检查来源，来源不匹配时拒绝调用 GPU 接口并提示刷新列表。CPU 操作继续只调用独立 CPU API。

**替代方案**：仅在前端根据 GPU 数量过滤。前端字段可能缺失或被伪造，且无法保护释放接口，因此必须在后端 DTO/服务层同时隔离。

### 5. 状态展示使用统一归一化映射

把 `creating`、`running`、`stopped`、`starting`、`stopping`、`releasing`、`released`、`failed`、`error` 归一化到统一标签和颜色。创建中和失败状态禁用不适用的操作；失败消息优先使用实例返回的状态说明、错误字段或服务端业务消息。

## Risks / Trade-offs

- [购买响应成功但列表暂时不可见] → 结果区保留实例 ID 和创建中状态，提供刷新入口；列表查询失败不覆盖已显示的受理结果。
- [上游没有返回来源字段] → 后端按明确 GPU 资源字段做保守判断；无法确认来源时不允许进入 GPU 释放路径，并记录联调问题。
- [旧数据缺少状态说明] → 使用通用状态文案，允许详情接口刷新后补充服务端消息。
- [CPU 与 GPU 页面共用组件引入条件分支] → 共享布局和基础状态组件，CPU/GPU 数据模型和操作处理仍保持独立。

## Migration Plan

1. 先扩展后端 GPU 列表 DTO/VO 和来源过滤，确保旧 GPU 接口响应字段兼容。
2. 更新前端 CPU 表单校验和创建中状态处理，再替换 CPU Tab 的布局和详情展示。
3. 移除实例管理页创建/购买入口，保留算力市场购买入口。
4. 联调创建成功、创建中、业务失败、网络超时、GPU/CPU 混源和释放保护场景。
5. 若上游来源字段不稳定，先关闭 GPU 释放操作并保留只读列表，避免误释放。

## Open Questions

- 上游 CPU 创建接口在“已受理但仍创建中”时是否会返回实例 ID；若不返回，需要通过订单号或列表中的创建时间窗口进行关联。
- 上游失败状态的正式枚举是否固定为 `failed`/`error`，还是存在其他状态值，需要在接口联调时补充映射。

## Implementation Note

当前门户适配层仍代理同步 CPU 购买接口，因此前端在响应成功且带实例记录时立即展示“创建中”，并对 CPU 列表进行最长十分钟的有界刷新；网络超时只展示“状态未知，请到列表确认”。要完全满足离页恢复、无实例 ID 占位和幂等重试，门户后端仍需要持久化租户级创建操作并返回 `operation_id`（或可查询的创建关联键），再提供状态查询接口。
